# Stage A persistence acceptance checklistSource: ChatGPT GPT-6 Astra, round 5 of the outside audit, written against main 78c5ed543650e8e304ab43363d062f93762ae58e. Reprinted here verbatim so it survives context compaction. Hebrew option letters are written as Alef, Bet, Gimel, Dalet.This is acceptance criteria, not a claim that any fix has landed. It is the standing bar for every persistence-related PR. Read it from this file, not from memory.## Test fixture and failure oracleT00 Exercise the UI. Start, answer, flag, navigate, finish, resume and export through the real controls, then inspect storage and a newly booted app. Calling only mockSaveRun(), hlSave() or bkGather() is insufficient to certify the corresponding control.T01 Fixed oracle. Use a seeded 100-question run with unique fixture IDs, four nonempty options per question, and an independently specified answer key. Call its first three questions Q1/Q2/Q3. Record their ordered IDs before editing; answer Q1=Alef, Q2=Bet, Q3=Gimel. Assertions must compare against the fixture, not copy the app's computed result as their expectation.T02 Controlled barriers. The storage double must hold individual reads and writes, release them in arbitrary order, reject a write, and acknowledge a write without persisting it. Record write invocation, durable commit, acknowledgment and readback separately. Use barriers, not sleep 500 ms and hope.T03 Two real app instances. A and B share persistent storage but have independent JS state and event loops. Capture alerts, confirmations, toasts, pending/failed-save status, exported bytes and persistent snapshots. Supply ordinary cross-tab notifications as well as delayed or missed notifications.T04 Restart means new memory. After each tested boundary, discard the DOM and reload from a copy of committed storage only. No pending promises or globals from the old instance may repair the copy after the simulated process stop.T05 Prove the tests bite. For each group below, remove or bypass that fix and show its designated negative case fails. Every test child must print a line exactly DONE; failed assertions or captured app errors must produce a nonzero exit. Capture errors from every app window. Wire these tests and harness-selftest.mjs into CI.## A. Stable mock identityID1 Identity survives normal work. Start R1; answer Q1/Q2, flag Q3, navigate backward and forward, reload, resume, and export/restore to a clean store. Assert the same nonempty run ID, identical ordered question IDs, answers, flags, cursor and original clock deadline throughout. Negative case: regeneration or omission of the run ID must fail.ID2 New run really is new. Decline the discard prompt: R1 and disk are byte-for-byte unchanged. Accept a new mock: R2 has a different ID even under a frozen timestamp and repeated RNG seed. Reload resumes R2, not R1.ID3 Safe migration. Load a real pre-fix checkpoint without a run ID. Resume without losing answers. Assign and durably retain one ID, or explicitly refuse migration while preserving an exportable original. Do not silently clear the old run.ID4 Identity is not corpus compatibility. Restore the same question IDs against fixture content whose option ordering or key changed. Reject or warn before reusing old choices; retaining the run ID alone must not certify that those choices still mean the same thing.## B. Serialized checkpoints and durable acknowledgmentSER1 The original rollback race. Commit R1 empty. Hold checkpoint C1 after answering Q1; answer Q2, producing C2. Assert C2 cannot commit before C1 if serialization is the chosen design. Release C1, drain the queue, restart: both answers survive and the revision order never moves backward. Negative case: permit overlapping writes, commit C2 then C1; the test must fail on the lost Q2 answer.SER2 Flags and cursor are in the same ordered state. While C1 waits, flag Q3, go back to Q1, change its choice, then move to Q3. Release, drain, restart. Assert the last answer, flag, cursor, ordered question list and unchanged deadline; no intermediate checkpoint may overwrite them.SER3 Rejection does not deadlock the queue. Reject C1; then allow a later complete checkpoint. The user sees a pending or failed-save state until recovery. Later edits must still commit; restart includes all acknowledged edits. A swallowed exception must not produce saved.SER4 False acknowledgment. Acknowledge C1 without changing disk. Assert readback and revision validation detect it and the UI and export do not claim the new answers are durable. Allow retry, then restart and verify recovery. Negative case: trusting the return value from set() alone must fail.SER5 Kill at the acknowledgment boundary. Snapshot and restart immediately before and after each checkpoint becomes durable. Every acknowledged edit survives. Before acknowledgment the UI must not claim it is saved. Do not define the impossible requirement that a killed page finishes an outstanding asynchronous write.## C. Stale-tab rejectionSTALE1 Two tabs opened before any run. Open A and B; A starts R1 and durably answers Q1 to Q7. B clicks Start. It must discover R1 and refuse or obtain explicit discard authorization; rejecting that prompt leaves all seven answers intact. Negative case: checking only B's mockOn or resume-button state must fail.STALE2 Captured Resume snapshot. Open B when R1 has two answers. A commits five more. B clicks its old Resume button. Assert it loads the seven-answer revision or reports a conflict; disk must never return to two answers.STALE3 Check/commit race. Both tabs read revision r. Hold B between validation and write; A commits r+1. Release B. Assert conditional commit or coordination rejects or safely reconciles B's stale write. A last-second read without an atomic ownership or revision mechanism must fail this test.STALE4 Late R1 write after R2 exists. Hold A's R1 checkpoint. In B explicitly replace R1 with R2 and commit R2. Release A. R2 and its answers remain unchanged; A is told its write was rejected. A different run ID in the payload alone is not protection unless the writer checks it.STALE5 Late completion must not erase a newer run. Hold A's Finish for R1 before its clear. Create and commit R2 in B, then release A. R2 remains resumable. Clear must be conditional on R1's identity and revision.STALE6 Conflicting answers. A and B change the same question from the same revision to different choices. Reject one with a visible conflict, or use an explicit, tested conflict policy. Never silently overwrite an answer while reporting both saves successful.END OF PART 1. Part 2 follows with D through G and the round-4 carryover.
## D. Finish only after answer records are durableFIN1 Hold the practice-result write. Answer seven questions, click Finish, and hold geri:pq. Let last-score and daily-log writes finish. Assert the recoverable run remains until the required answer records are verified. Kill and restart at this point: all seven original answers remain recoverable. Negative case: a fire-and-forget pqSave() followed by clearing the run must fail.FIN2 Reject each finish write. Independently throw and silently drop the practice-result, mock daily-log, last-score and run-clear writes. The app must retain sufficient recovery state, name the unsaved or partial outcome, and never present an entirely saved completion while required records are missing.FIN3 Interrupt every commit boundary. Stop after each finish-stage durable write. Restart must produce either a resumable original run or a recoverable or committed completed transaction; never no run and no answers. Define and assert the recovery state explicitly.FIN4 Idempotent completion. Double-click Finish; retry after a partial failure; reload during recovery. Assert no duplicate history entry, duplicate question result, or repeated score aggregation for the same run and revision.FIN5 Timer follows the same transaction. Repeat FIN1 to FIN4 with automatic clock expiry instead of the Finish button. Preserve blanks separately from answered-wrong questions. Expiry while backgrounded must not bypass durability checks.## E. Preserve edits made during an annotation saveANN1 Text replacement while saving. From an empty store, type FIRST in the falls note; allow its debounce to start and hold its write. Type SECOND; allow the next save to queue. Release the first write. Assert live state, focused textarea, exported backup and restart all contain SECOND. Negative case: applying the old merged object over current state must fail.ANN2 Two genuine selections. Highlight passage A, hold its save, then highlight distinct passage B. Release, drain, restart. Both anchors, remarks and colors survive; both marks are painted in their original sections. Assert actual selection and DOM behaviour, not just object length.ANN3 Edit and delete, not just append. While an earlier save waits, edit a highlight's remark and color and delete another highlight. On completion and restart the new remark and color remain and the deleted item is not resurrected. Clearing a section note must likewise remain a deletion.ANN4 Older repaint cannot erase typing. Hold readback and repaint, edit again, blur the field, then release it. The newer text must not disappear merely because document.activeElement changed. Revision-aware state, not focus alone, must protect the edit.ANN5 Failed first save. Repeat ANN1 to ANN3 with rejection and with false acknowledgment of the first write. The latest live edit stays recoverable; show not-saved status; allow a subsequent retry to persist it. No queued save may serialize an already-reverted object.## F. Cross-tab practice-result mergePQ1 Different questions, sequential tabs. Open A and B on an empty store. A answers Q1 and commits. B answers Q2 from its old local state. Reload both: Q1 and Q2 are present, exactly once, with their independently expected outcomes. Negative case: writing B's whole stale pqDone object must fail.PQ2 Both read before either writes. Hold both merge reads after they observe the same old revision. Commit A/Q1, then release B/Q2. Repeat with reverse ordering. The union survives in both orders; a naive read-merge-write implementation must fail.PQ3 Mock completion versus ordinary practice. Hold a mock's batch result commit in A. In B commit an ordinary practice answer for an unrelated question. Release A. Both the mock's results and B's answer remain after restart.PQ4 Same-question conflict has a policy. A and B answer the same question differently from the same base version. Assert the documented resolution using a version, order or conflict marker, not an accidental delayed-writer overwrite. Unrelated results must survive whichever policy wins.PQ5 Failure and retry do not duplicate or roll back. Reject or silently drop one merge write, allow the other tab to commit, then retry the failed write. Assert a correct union, visible failure status before recovery, and no duplicate counts or history entries.## G. Backup flushes or plainly reports stale dataBK1 Pending note debounces. Type both a weekly note and a section note, then immediately click Download before either debounce fires. Restore the exported bytes into a clean instance. Both notes must be present; otherwise export must stop or visibly say the backup omits these pending edits. A saved badge alone is a failure.BK2 Pending annotation save, both paths. Hold a highlight or section-note write after it enters the queue. Invoke Download, then separately Copy backup. Each must wait for completion or explicitly report that the output is stale. Release the write; restore the resulting file and JSON and verify the edit. Negative case: fixing bkGather() while leaving bkFill() unchanged must fail.BK3 Pending mock checkpoint. Hold the save after Q3 while disk has only Q1 and Q2. Click Download and Copy separately. A backup advertised as current must resume with all three answers, the same run ID, flags, position, ordered IDs and deadline. Otherwise the UI must explicitly say Q3 and current mock changes are not included.BK4 Refused persistence and misleading recovery advice. Throw, then separately falsely acknowledge, the latest answer or note save. Follow the app's own download a backup advice. Require an accurate export of the recoverable current state or a plain, visible stale or failed-backup warning. Do not hand the user old bytes while implying this rescued the new work.BK5 Edit during export. Hold an export read; make another edit locally and in the other tab. Resume export. The result must be one documented consistent revision or snapshot, or carry a clear staleness or conflict warning. It must not silently mix a new run's ID with an old run's questions and answers.BK6 Queue failure or timeout. A pending save rejects or never resolves. Export must reach an explicit recoverable failure or stale decision; no endless spinner and no successful-download message for an incomplete snapshot.BK7 Real restore oracle. Parse the actual Blob or download bytes and the actual copied text; restore each into a clean store, reload, click Resume, and inspect notes and highlights. Merely asserting that a key exists in the backup object does not pass.## Additional release blocker carried from round 4XANN Concurrent annotation merge is separate from in-flight edit preservation. Hold B's read of empty annotations. A commits a falls note or highlight and verifies it. Release B to commit a delirium note or highlight based on the old read. Both sections must survive in both write orders, without falsely reporting successful preservation. Fixing ANN1 alone does not fix this race.END OF FILE.
